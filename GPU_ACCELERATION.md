## Integration path

1. The Android 17 tree contains `device/google/sdv/prebuilts` with an ARM64 Mesa VirGL `libGLES_mesa`, `gallium_dri`, and `virtio_gpu_dri.so` symlink. The Kiki product branch adds that namespace and package while retaining Ranchu HWC3 and minigbm.
   The first targeted build exposed a page-size mismatch: all three upstream SDV Mesa prebuilts use 4 KiB ELF LOAD alignment, while the product's general prebuilt check requires 16 KiB. 2. The Windows launcher branch has opt-in `-GpuMode Virgl`, selecting `virtio-gpu-gl-pci`, GTK OpenGL, and `androidboot.hardwareegl=mesa`. Default `Software` mode keeps the previous arguments. `-DryRun` prints the argument vector without starting QEMU.
3. Build and collect a new system/vendor image pair. Run the complete launcher only with that pair. Verify SurfaceFlinger's GLES renderer is VirGL rather than SwiftShader, confirm Adreno GPU activity on Windows, and inspect HWC/minigbm buffer import and presentation. `-GpuBlob` is an opt-in QEMU experiment for shared GPU memory; verify the guest DRM feature flags before benchmarking it.
4. Benchmark portrait and large-window frame times, touch latency, dynamic resolution, audio, and long-running stability. Optimize host presentation only if measurement points there. Do not claim 30–60 FPS until a repeatable workload demonstrates it.

Venus is therefore a promising separate route for Vulkan workloads, but it is not enabled or validated in this image and cannot yet be counted as acceleration. It will need a compatible guest Venus Vulkan HAL and a full-system test. See [QEMU virtio-gpu options](https://www.qemu.org/docs/master/system/devices/virtio/virtio-gpu.html), [virglrenderer Venus capset](https://android.googlesource.com/platform/external/virglrenderer/+/refs/heads/main/src/venus_hw.h), and Microsoft's [OpenGL-on-D3D12 mapping-layer overview](https://devblogs.microsoft.com/directx/in-the-works-opencl-and-opengl-mapping-layers-to-directx/).

## Fixed-resolution frame-wait diagnosis

The benchmark now uses `GL_EXT_disjoint_timer_query` with a four-query asynchronous ring (results are polled only when available), and separately records CPU wall time, GL-thread CPU time, and the `glClear`/state/buffer/draw-call portions. Android confirms `GL_RENDERER=virgl`, GLES 3.1, `GLSurfaceView=864x1728`, and `wm size=864x1728` throughout these measurements.

The supported launcher enforces 864x1728 as the minimum portrait mode (including either orientation by validating the shorter and longer sides) and rejects smaller dimensions. Performance comparisons must keep that floor and must not use internal render scaling.

At this unchanged minimum resolution:

| Profile | GPU time for the instanced draw | `glClear` wall time | GL-thread CPU time | Observed FPS |
| --- | ---: | ---: | ---: | ---: |
| 60-FPS target, 1,024 instances | 0.5–1.2 ms | 48–51 ms | 1.3–2.9 ms | 17–20 |
| Extreme, 32,768 instances | 4.4–8.3 ms | 47–56 ms | 0.9–5.5 ms | 16–19 |

The draw submission itself takes roughly 0.03–0.08 ms and query polling about 0.02–0.09 ms. The measured `glClear` wall time is mostly a wait, not clear-command CPU work; guest GL-thread CPU consumption remains low. Reducing guest resolution or render scale would hide rather than solve it and is prohibited by the fixed 864x1728 baseline.

In a five-second SurfaceFlinger sample during Extreme, GPU missed-frame count rose by 93, HWC missed-frame count stayed at zero, and the framebuffer output counter advanced by 88. These counts track the roughly 18-FPS producer, but do not on their own prove the Windows GTK refresh rate is the root cause.

A short Android `atrace gfx view sched` capture provides a more specific guest-side wait: `GLThread 16` repeatedly enters `dequeueBuffer` → `waitForBufferRelease` for the app's `SurfaceView` and sleeps for about 33–54 ms before the release callback. In the same trace, the matching HWC release-fence signal arrives immediately before the producer is woken. SurfaceFlinger reports `usesClientComposition=true`, a 60 Hz virtual display, and a `FramebufferSurface` queue with `mMaxAcquiredBufferCount=1` and `mMaxDequeuedBufferCount=1`; the app's SurfaceView has three imported buffers. This confirms buffer-release backpressure in the frame path, not an undersized guest mode. Android's graphics synchronization contract requires a producer to wait for a buffer's release fence before reusing it ([AOSP synchronization framework](https://source.android.com/docs/core/graphics/sync)). The trace does not yet establish whether the long fence is caused by guest RenderEngine composition, QEMU/VirGL fence servicing, or GTK/WGL scanout; those stages still need host-side timing.

The host-only WGL probe was also used to test virglrenderer synchronization flags before changing QEMU. `VIRGL_RENDERER_THREAD_SYNC` alone allowed `virgl_renderer_init()` but `virgl_renderer_get_poll_fd()` returned `-1`, so the worker-sync path was not active in this build; adding the flag in QEMU would be a no-op. `VIRGL_RENDERER_ASYNC_FENCE_CB | VIRGL_RENDERER_THREAD_SYNC` with no EGL display failed initialization (`failed to get egl display`). No such experimental flag was added to QEMU. Next, correlate host-side QEMU/VirGL fence submission and completion with the guest release-fence timestamps; only then test a synchronization or presentation change. Keep the known-good QEMU and 864x1728 mode unchanged until an alternative passes the same end-to-end test.

### Fence-poll interval A/B

The Windows WGL path has no `qemu_egl_display`, so QEMU does not enable virglrenderer async-fence callbacks and falls back to `virgl_renderer_poll()` with a 10 ms re-arm while commands/fences remain pending (`hw/display/virtio-gpu-virgl.c`). Because the timestamped trace showed a response tail near 10 ms, I tested changing only that fallback interval to 1 ms. Both runs used the same 8-vCPU, blob-enabled GTK launch, Extreme 32,768-instance scene, and 864x1728 guest mode.

In the matched five-second trace windows, the 10 ms baseline produced 262 matched fences (1.739 ms median, 9.630 ms p95, 25.667 ms maximum); the 1 ms experiment produced 253 (1.204 ms median, 9.094 ms p95, 17.135 ms maximum). This modestly shortened the observed fence tail, but did not translate into a repeatable frame-rate gain: the 1 ms run's ten-second steady sample was 17.27 FPS median (16.07–17.84), with 52.87 ms median `glClear` wall time. The untraced 10 ms baseline was 17.48 FPS median with 52.62 ms `glClear` wall time. Given the overlapping FPS range and lack of practical improvement, I reverted the 1 ms timer change; the reproducible QEMU build remains at the upstream 10 ms interval. The large wait is still downstream or in another synchronization stage, so poll frequency is not the fix for the 60-FPS goal.

The minimum guest mode remains **864x1728 at 60 Hz**. The benchmark is still the same Extreme 3D scene with **32,768 instances**; no render-scale or workload reduction was used. It measured 37.79 FPS median over 56 windows, versus 41.75 FPS in the previous two-buffer run; different-run variance is large, so this is not a trustworthy regression, but it provides no evidence of a gain. The experimental `ro.surface_flinger.max_frame_buffer_acquired_buffers=3` property was removed from the device tree. A separate 8-vCPU HWC comparison also showed no material distinction: Client median 28.89 FPS and Guest median 30.54 FPS over 41 windows each, with overlapping ranges and substantial time variation. No HWC mode switch is claimed as an optimization.

The remaining bottleneck is synchronization/backpressure. In the latest samples, GPU instanced-draw time was roughly 4.5–4.8 ms and GL-thread CPU about 2.5 ms, while `glClear` wall time varied around 28–32 ms and FPS varied from the low 20s to low 40s. Windows attributed roughly 12–23% Adreno X1-85 3D-engine utilization to the QEMU process; total host CPU was about 14–16%. The GPU is genuinely engaged but neither aggregate host CPU nor the 3D engine was saturated. Keep investigating the BufferQueue/release-fence and QEMU present/synchronization path rather than changing resolution.

The host QEMU build exposes `venus=on`; a small host-only `virtio-gpu-gl-pci,blob=on,venus=on` smoke VM initialized and remained alive, then was shut down through its monitor. This only establishes host-side initialization, not Android Vulkan acceleration. The guest currently has `/vendor/lib64/hw/vulkan.pastel.so` and `ro.hardware.vulkan=pastel`; AOSP builds that Pastel module from SwiftShader, so Vulkan apps currently use a software renderer. The Android 17 Mesa source checkout contains `src/virtio/vulkan` (`vulkan_virtio`/Venus) sources. A temporary Soong target for the guest Venus HAL compiled successfully, but was not included in an image. The Surface runtime is Windows ARM64/MSYS2, where the QEMU build links virglrenderer 1.3.0; the installed package metadata advertises the GL renderer/epoxy dependency and not Vulkan, and a DLL string check found no Venus/Vulkan markers. Mesa's [Venus requirements](https://docs.mesa3d.org/drivers/venus.html) describe Linux Vulkan/external-memory-fd requirements and tested Linux drivers; QEMU's [Vulkan pass-through requirements](https://www.qemu.org/docs/master/system/devices/virtio/virtio-gpu.html) are Linux-host-specific. Thus QEMU accepting `venus=on` and compiling a guest HAL do not establish a working Windows Venus path. I removed the unverified trial from the product, launcher, and temporary AOSP overlay; no image or stable baseline was changed. Keep this separate from the proven VirGL GLES path.

The hard floor remains **864×1728** (or the same dimensions in landscape), and the benchmark remains the same Extreme 3D scene with **32,768 instances**. The launcher rejects smaller sizes, while the app sets `glViewport` to the actual `GLSurfaceView` pixels. No render-scale, guest-size, or workload reduction is allowed for an FPS result. The tests did not establish a stable 60-FPS result. The benchmark window was closed after capture; no QEMU process or ADB transport remains from this test.

Next performance work stays on the proven Windows WGL + VirGL GLES route: preserve the 864×1728 mode and 32,768-instance workload, then trace guest buffer-release/present waits against host WGL/virglrenderer completion. Do not use lower resolution or internal render scaling as a workaround.
