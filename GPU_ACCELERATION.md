## Crash boundary

At about 01:06 local time, a bare QEMU experiment without a kernel or firmware was followed by an unexpected Windows reboot. The first invocation used WHPX, `virtio-gpu-gl-pci`, and `gtk,gl=on`; it exited with code 1. A second bare WHPX invocation using the 2D GPU and `gtk,gl=off` was interrupted by the reboot. Event 41 confirms an unclean reboot, but BugcheckCode was 0 and no useful dump was found, so the triggering operation is not proven. Do not repeat either bare-WHPX probe. Future guest tests must use the complete, previously bootable kernel/ramdisk/partition command generated by `tools/run_kikiaosp_touch_local.ps1`.

The first *complete* Android/VirGL attempt (`gpu-virgl-first-20260927`) failed before guest kernel output. Windows WER recorded QEMU exception `0xc0000005`; LLDB resolved the dump at `C:\Users\keke\AppData\Local\CrashDumps\qemu-system-aarch64.exe.20488.dmp` to `ui/gtk.c:2733`, `gl_area_realize()` calling `eglGetCurrentDisplay()` through a null dispatch address. The Windows GtkGLArea is WGL-backed, not EGL-backed. `patches/qemu-windows-gtk-glarea-wgl.patch` skips that call only for a Win32 GDK display. The QEMU executable was rebuilt incrementally, remains PE ARM64, and the second complete boot passed this crash point. This WER crash was an application failure, not another Windows reboot.

The host-only WGL/VirGL probe now passes after giving `virgl_renderer_init()` a non-null cookie: `GL_RENDERER=D3D12 (Qualcomm(R) Adreno(TM) X1-85 GPU)`, `VIRGL_INIT=0`, capset 1 version 1, size 308. This probe does not use QEMU or WHPX.

## Integration path

1. The Android 17 tree contains `device/google/sdv/prebuilts` with an ARM64 Mesa VirGL `libGLES_mesa`, `gallium_dri`, and `virtio_gpu_dri.so` symlink. The Kiki product branch adds that namespace and package while retaining Ranchu HWC3 and minigbm.
   The first targeted build exposed a page-size mismatch: all three upstream SDV Mesa prebuilts use 4 KiB ELF LOAD alignment, while the product's general prebuilt check requires 16 KiB. The Kiki branch disables that prebuilt check for this 4 KiB-kernel experiment while leaving other modules' 16 KiB linker setting intact. This GPU image is **not** 16 KiB compatible until Mesa is rebuilt with 16 KiB alignment.
2. The Windows launcher branch has opt-in `-GpuMode Virgl`, selecting `virtio-gpu-gl-pci`, GTK OpenGL, and `androidboot.hardwareegl=mesa`. Default `Software` mode keeps the previous arguments. `-DryRun` prints the argument vector without starting QEMU.
3. Build and collect a new system/vendor image pair. Run the complete launcher only with that pair. Verify SurfaceFlinger's GLES renderer is VirGL rather than SwiftShader, confirm Adreno GPU activity on Windows, and inspect HWC/minigbm buffer import and presentation. `-GpuBlob` is an opt-in QEMU experiment for shared GPU memory; verify the guest DRM feature flags before benchmarking it.
4. Benchmark portrait and large-window frame times, touch latency, dynamic resolution, audio, and long-running stability. Optimize host presentation only if measurement points there. Do not claim 30–60 FPS until a repeatable workload demonstrates it.

## Current performance and next experiment

A controlled portrait test at 864×1728 brought Settings to the foreground, reset `dumpsys gfxinfo`, then injected seven vertical swipes. It rendered 91 frames: 87 janky (95.6%), with a 69 ms median, 117 ms 90th percentile, and 150 ms 95th percentile. The same report showed a 6 ms median and 15 ms 90th percentile GPU duration, while 83 frames had slow draw-command issue time. This is consistent with time being spent in guest/QEMU command submission or synchronization; it does not yet prove which side is responsible. It is far from the 30–60 FPS daily-use target even though the user sees a clear improvement over the software route.

The QEMU build links virglrenderer 1.3.0. The original no-blob run negotiated `+virgl +edid -resource_blob -host_visible`; the later opt-in `-GpuBlob` run negotiated `+resource_blob +host_visible` and booted at the same 864×1728 mode, but did not produce a material FPS improvement. Keep blob mode optional until a later end-to-end test shows stability and a measurable gain. The Android SDV Mesa prebuilt remains 20.3.4 (2021-era) and is a candidate for later profiling; replacing it before resolving the host synchronization bottleneck would confound the comparison.

The upstream references for this path are the [QEMU virtio-gpu documentation](https://www.qemu.org/docs/master/system/devices/virtio/virtio-gpu.html) and [AOSP Cuttlefish GPU modes](https://source.android.com/docs/devices/cuttlefish/gpu).

## Fixed 864×1728 performance baseline

The minimum usable portrait guest mode is fixed at **864×1728, 60 Hz**. The launcher now rejects startup display dimensions whose short side is below 864 or long side below 1728; landscape 1728×864 is accepted. The Android benchmark sets `glViewport()` to the actual `GLSurfaceView` dimensions and reports them on screen/logcat. No benchmark result is accepted after lowering guest resolution or using internal render scaling. The current full-desktop evidence, with QEMU left windowed and Android rendering the Extreme 3D scene, is `C:\Users\keke\Downloads\temp\qemu-desktop-gpu-bench-extreme-fixed-864x1728-20260927.png`.

At 864×1728, the 8-vCPU VirGL/blob run reports about **15–19 FPS** for the light “60 FPS target” profile and **13–19 FPS** for “Extreme 3D” (32,768 instanced objects; the fragment shader executes its 24-iteration ceiling). The guest display mode remains 60 Hz. On the host, QEMU's Adreno 3D engine sampled about 8% under the light profile and 18% under Extreme; a separate WGL probe identifies the host GL renderer as `D3D12 (Qualcomm(R) Adreno(TM) X1-85 GPU)`. The GPU is active, but low/medium utilization alongside poor frame rate points toward work submission/synchronization rather than simply insufficient pixel throughput. These are diagnostic measurements, not a 30–60 FPS success claim.

The Windows GTK frontend uses WGL `GtkGLArea`; the crash-avoidance patch deliberately sets `qemu_egl_display=EGL_NO_DISPLAY`. In upstream QEMU's VirGL implementation, `VIRGL_RENDERER_ASYNC_FENCE_CB` and `VIRGL_RENDERER_THREAD_SYNC` are enabled only when an EGL display is present. This makes a proper Windows EGL/context-sharing route a strong next synchronization experiment; blindly enabling those flags with the current WGL context is not justified. QEMU's host-memory blob option was already tested at the fixed resolution and did not produce a material FPS increase.

The host also exposes Qualcomm's native Adreno Vulkan 1.4 driver and Mesa Dozen Vulkan over D3D12. The guest currently contains only `vulkan.pastel.so` (software Vulkan), while QEMU/virglrenderer has a Venus capset path that requires blob and host memory. Venus is therefore a promising separate route for Vulkan workloads, but it is not enabled or validated in this image and cannot yet be counted as acceleration. It will need a compatible guest Venus Vulkan HAL and a full-system test. See [QEMU virtio-gpu options](https://www.qemu.org/docs/master/system/devices/virtio/virtio-gpu.html), [virglrenderer Venus capset](https://android.googlesource.com/platform/external/virglrenderer/+/refs/heads/main/src/venus_hw.h), and Microsoft's [OpenGL-on-D3D12 mapping-layer overview](https://devblogs.microsoft.com/directx/in-the-works-opencl-and-opengl-mapping-layers-to-directx/).

## Fixed-resolution frame-wait diagnosis

The benchmark now uses `GL_EXT_disjoint_timer_query` with a four-query asynchronous ring (results are polled only when available), and separately records CPU wall time, GL-thread CPU time, and the `glClear`/state/buffer/draw-call portions. Android confirms `GL_RENDERER=virgl`, GLES 3.1, `GLSurfaceView=864x1728`, and `wm size=864x1728` throughout these measurements.

The supported launcher enforces 864x1728 as the minimum portrait mode (including either orientation by validating the shorter and longer sides) and rejects smaller dimensions. Performance comparisons must keep that floor and must not use internal render scaling.

At this unchanged minimum resolution:

| Profile | GPU time for the instanced draw | `glClear` wall time | GL-thread CPU time | Observed FPS |
| --- | ---: | ---: | ---: | ---: |
| 60-FPS target, 1,024 instances | 0.5–1.2 ms | 48–51 ms | 1.3–2.9 ms | 17–20 |
| Extreme, 32,768 instances | 4.4–8.3 ms | 47–56 ms | 0.9–5.5 ms | 16–19 |

The draw submission itself takes roughly 0.03–0.08 ms and query polling about 0.02–0.09 ms. The measured `glClear` wall time is mostly a wait, not clear-command CPU work; guest GL-thread CPU consumption remains low. Reducing guest resolution or render scale would hide rather than solve it and is prohibited by the fixed 864x1728 baseline.

In a five-second SurfaceFlinger sample during Extreme, GPU missed-frame count rose by 93, HWC missed-frame count stayed at zero, and the framebuffer output counter advanced by 88. These counts track the roughly 18-FPS producer, but do not on their own prove the Windows GTK refresh rate is the root cause.

A short Android `atrace gfx view sched` capture provides a more specific guest-side wait: `GLThread 16` repeatedly enters `dequeueBuffer` → `waitForBufferRelease` for the app's `SurfaceView` and sleeps for about 33–54 ms before the release callback. In the same trace, the matching HWC release-fence signal arrives immediately before the producer is woken. SurfaceFlinger reports `usesClientComposition=true`, a 60 Hz virtual display, and a `FramebufferSurface` queue with `mMaxAcquiredBufferCount=1` and `mMaxDequeuedBufferCount=1`; the app's SurfaceView has three imported buffers. This confirms buffer-release backpressure in the frame path, not an undersized guest mode. Android's graphics synchronization contract requires a producer to wait for a buffer's release fence before reusing it ([AOSP synchronization framework](https://source.android.com/docs/core/graphics/sync)). The trace does not yet establish whether the long fence is caused by guest RenderEngine composition, QEMU/VirGL fence servicing, or GTK/WGL scanout; those stages still need host-side timing.

The host-only WGL probe was also used to test virglrenderer synchronization flags before changing QEMU. `VIRGL_RENDERER_THREAD_SYNC` alone allowed `virgl_renderer_init()` but `virgl_renderer_get_poll_fd()` returned `-1`, so the worker-sync path was not active in this build; adding the flag in QEMU would be a no-op. `VIRGL_RENDERER_ASYNC_FENCE_CB | VIRGL_RENDERER_THREAD_SYNC` with no EGL display failed initialization (`failed to get egl display`). No such experimental flag was added to QEMU. Next, correlate host-side QEMU/VirGL fence submission and completion with the guest release-fence timestamps; only then test a synchronization or presentation change. Keep the known-good QEMU and 864x1728 mode unchanged until an alternative passes the same end-to-end test.

### SDL frontend A/B at the fixed resolution

To check whether GTK presentation was the limiting factor, the launcher gained an opt-in `-DisplayBackend sdl` switch; GTK remains the default. The first SDL VirGL launch crashed in QEMU's `ui/sdl2.c`: SDL creates a WGL context on Windows, but upstream code unconditionally called `eglGetCurrentDisplay()`. The reproducible Windows-only fix is `patches/qemu-windows-sdl-gl-wgl.patch`, applied by `tools/build_qemu_arm64.sh`; like the existing GTK WGL fix, it exposes `EGL_NO_DISPLAY` rather than passing a WGL context to EGL. The rebuilt QEMU then booted the complete Android system successfully.

The SDL comparison kept the guest at **864x1728** and ran the same Extreme benchmark, but SDL exposed a 75 Hz mode while GTK exposed 60 Hz, so it is diagnostic rather than a perfectly refresh-matched A/B. SDL measured roughly **10–14 FPS**, 5–8 ms GPU draw time, 61–108 ms `glClear` wall time, and about 5% sampled Adreno 3D utilization. Returning to GTK at 864x1728 restored the stable path; the captured Extreme frame showed **16.8 FPS**, 6.31 ms GPU draw, and 0.03 ms CPU draw submission. SDL therefore did not improve throughput and is not the default. Evidence is in `bundles/gpu-virgl-native-20260927/qemu-kikiaosp-gpu-sdl-ab-fixed-864x1728-20260927.*` and `.../qemu-kikiaosp-gpu-gtk-restored-864x1728-20260927.*`; the full desktop capture is `C:\Users\keke\Downloads\temp\qemu-desktop-gpu-gtk-restored-fixed-864x1728-20260927.png`.

The fixed **864x1728 minimum is a hard benchmark invariant**. Do not reduce guest mode, render scale, or benchmark resolution to raise the FPS number. The present result remains below target; continue tracing the buffer-release/fence wait and host VirGL presentation path. Windows GPU ETW capture could not be started under the current account policy, so this experiment used read-only Windows GPU-engine utilization sampling instead; do not treat that utilization snapshot as a precise per-frame attribution.

### Live QEMU fence trace

The current QEMU build supports selecting trace events and redirecting its log at runtime through HMP. In the initial short sample during the same Extreme scene, **3,398 `virtio_gpu_fence_ctrl` and 3,398 matching `virtio_gpu_fence_resp` events** were counted, with every captured fence ID having a response. I mistakenly assumed HMP `log none` also disabled dynamic trace events; it only changed the log mask. The trace therefore continued longer than intended and the file ultimately reached **10,190 matching pairs** before I explicitly disabled the events at 05:43:50 local time. Because the trace has no timestamps, its exact active interval and per-fence latency cannot be recovered; benchmark readings during the extended logging interval are not valid performance results. The raw file is `bundles/gpu-virgl-native-20260927/qemu-kikiaosp-gpu-fence-live-20260927.log`; it stopped growing after I used `trace-event virtio_gpu_*fence* off` and verified all four matching event states were 0. The running 864x1728 GTK guest remained booted.

After explicitly disabling tracing, the same live Extreme run produced ten consecutive one-second windows at 864x1728: median **17.48 FPS** (16.20–18.64), median `CLEAR_MS` **52.62 ms** (48.51–56.56), median GL-thread CPU **1.31 ms** (0.97–2.10), and median GPU draw **6.89 ms** (6.35–8.96). The trace file remained byte-for-byte stable during this sample. This confirms that low throughput persists without trace overhead; the large clear-call wall time is predominantly off-CPU waiting, while measured GPU draw is much shorter. It still does not identify which side of the guest/host fence causes that wait.

For the next controlled run, `tools/run_kikiaosp_touch_local.ps1 -TraceVirglFences` now enables only the QEMU virtio-gpu fence request/response events, adds QEMU message timestamps, and writes a unique per-run `*.qemu-trace.log` beside the bundle logs. The new `tools/qemu-virgl-fence-events.txt` is the event allowlist. The launcher refuses to overwrite a prior trace and requires `-GpuMode Virgl`. This makes the next sample suitable for pairing request/response timestamps while keeping the benchmark resolution and workload unchanged. It remains opt-in; ordinary GTK launches and performance numbers are unaffected.
